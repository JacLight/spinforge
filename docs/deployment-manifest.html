SpinForge · Developer Reference

The deployment manifest

Describe your project once in a file, POST it, and SpinForge clones your repo, builds it, and puts it on your domain. Re-run it on every push — applying is idempotent.

formatYAML or JSON filenamespinforge.yaml endpointPOST /_api/customer/manifest requiredname + repo.url authBearer sfc_…

Quick start

  1. Get an API token

    You need a long-lived customer token — it starts with sfc_. Create one from your account settings in the dashboard. The token identifies you as the owner of everything you deploy.

  2. Add spinforge.yaml to your repo

    Two fields are required. Everything else has a default.

    name: my-app
repo:
  url: https://github.com/me/my-app

    Prefer JSON? Same fields, same endpoint:

    {
  "name": "my-app",
  "repo": { "url": "https://github.com/me/my-app" }
}
  3. Send it 
    curl -X POST https://build.spinforge.dev/_api/customer/manifest \
  -H "Authorization: Bearer sfc_your_token" \
  -H "Content-Type: application/yaml" \
  --data-binary @spinforge.yaml

    SpinForge creates the pipeline and starts a build immediately. You get back the pipeline id, the build id, and any warnings.

YAML or JSON — both work

Write whichever you prefer. The same parser reads both, so the fields, defaults, and validation are identical. Set Content-Type to match what you send:

You sendContent-Typecurl flag
spinforge.yamlapplication/yaml--data-binary @file
spinforge.jsonapplication/json--data @file

text/yaml, application/x-yaml, and text/x-yaml are accepted too. Use --data-binary for YAML so curl preserves newlines — plain --data strips them and the document won't parse.

Unknown fields are rejected rather than ignored, so a typo like domian fails loudly instead of being silently dropped.

Editor support

The schema is published, so your editor can autocomplete fields and flag mistakes as you type. Add $schema to a JSON manifest:

{
  "$schema": "https://build.spinforge.dev/_api/customer/manifest/schema",
  "name": "my-app"
}

For YAML, map it once in your editor settings — in VS Code with the YAML extension:

"yaml.schemas": {
  "https://build.spinforge.dev/_api/customer/manifest/schema": "spinforge.yaml"
}

Fetch it directly with GET /_api/customer/manifest/schema. It is draft-07 and is generated from the same definition the server validates against, so it can never drift out of sync.

A complete manifest

Every field, shown with its default. Only name and repo.url are required — most manifests are three lines.

name: my-app                     # required

repo:
  url: https://github.com/me/my-app   # required
  ref: main                         # default: the repo's default branch
  token: ghp_…                      # private repos only

domain: app.example.com            # default: <name>.spinforge.dev
type: static                       # static | node | container
rootDir: apps/web                  # default: .  (monorepo subdirectory)
aliases:
  - www.app.example.com

owner:
  email: me@example.com            # verified against your account
  name: Jane Doe

autoDeploy: true                  # false = save config, don't build

Field reference

FieldTypeDefaultNotes
namestringrequired1–100 chars. Re-applying with the same name updates that deployment instead of creating a second one.
repo.urlstringrequiredGit clone URL, HTTPS or SSH.
repo.refstringdefault branchBranch, tag, or SHA. Defaults to whatever the repo's default branch is.
repo.tokenstring—PAT for private repos. Never returned in a response.
domainstring<name>.spinforge.devAuto-assigned and collision-checked if omitted. Never changes once assigned.
typeenumstaticstatic, node, or container.
rootDirstring.Subdirectory holding the project, for monorepos.
aliasesstring[][]Extra domains pointing at the same site.
owner.emailemail—Verified against your account. A mismatch is rejected with 403.
owner.namestring—Display name only.
autoDeploybooleantrueSet false to save the configuration without building.

$schema and $comment are accepted and ignored by the server.

No build customization

Build command, output directory, package manager, and Node version are fixed: npm ci && npm run build producing dist. A project using yarn or pnpm, or writing to build/, cannot deploy through a manifest yet.

Project types

Defaults to static. Set it explicitly for node or container.

TypeUse forWhat runsStatus
static Vite, Next export, Astro, plain HTML build.static → deploy.static-site Deploys
node Node apps with a build step build.node → deploy.static-site Deploys
container Anything with a Dockerfile build.container → deploy.container Not yet
Container support is incomplete

A container manifest validates and saves, but nothing is built or deployed — those two steps have no runner yet. The build will report success having done nothing, so SpinForge tells you up front: every apply returns a warning naming the skipped steps. Use static or node until this lands.

Endpoints

Apply a manifest

POST /_api/customer/manifest

Creates the deployment on first call (201), updates it on every call after (200). Starts a build unless autoDeploy is false.

{
  "created":  true,
  "domain":   "app.example.com",
  "pipeline": { "id": "pl_01J…", "name": "my-app", "stages": [ … ] },
  "build":    { "id": "bld_01J…", "status": "queued" },
  "warnings": []
}

Check a manifest without applying it

POST /_api/customer/manifest/validate

Same body, no side effects. Returns the resolved type and the steps that would run. Good for a CI pre-check.

{
  "valid":  true,
  "type":   "static",
  "domain": "app.example.com",
  "stages": [
    { "id": "build",  "action": "build.static" },
    { "id": "deploy", "action": "deploy.static-site" }
  ],
  "unsupported": []
}

Fetch the schema

GET /_api/customer/manifest/schema

Public — no auth. Mounted before the auth gate so editors resolving $schema can fetch it. Returns application/schema+json.

Authentication

Send your token either way:

Authorization: Bearer sfc_your_token
x-auth-token: sfc_your_token

Errors

An invalid manifest returns 400 with one entry per problem, each pointing at the exact path that failed.

{
  "error":   "manifest_invalid",
  "message": "manifest validation failed",
  "details": [
    { "path": "/repo", "message": "must have required property 'url'" },
    { "path": "/type", "message": "must be equal to one of the allowed values" }
  ]
}

Wrong account

A declared owner that does not match your token returns 403:

{
  "error":   "owner_mismatch",
  "message": "manifest owner.email \"x@y.com\" does not belong to the authenticated account — check you are using the right API token"
}

Common causes

  • A misspelled field name — unknown properties are rejected, not ignored.
  • Missing name, domain, or repo.url.
  • A type outside static / node / container.
  • A malformed owner.email.
  • YAML sent with curl --data instead of --data-binary, which strips the newlines.

A malformed document fails before validation and tells you where:

{
  "error":   "manifest_invalid",
  "message": "could not parse manifest as YAML at line 2, column 6: bad indentation of a mapping entry"
}

Your domain

Leave domain out and SpinForge assigns <name>.spinforge.dev, slugified from the name. Availability is checked against every site on the platform — including platform domains like admin and api — and a numeric suffix is added on a clash (my-app-2, my-app-3).

Once assigned, the domain is reused on every later apply. Re-running a manifest never moves a live site to a new address.

Monorepos

rootDir points at the subdirectory holding the project. The repo is cloned whole; the build runs from there and output paths resolve against it.

name: web
rootDir: apps/web
repo:
  url: https://github.com/me/monorepo

Runs cd apps/web && npm ci && npm run build with output at apps/web/dist. Paths that escape the clone are rejected.

Things worth knowing

Your token owns the deployment

Ownership is taken from the sfc_ token, never from owner.email — otherwise anyone could claim a domain by typing your address into a file. When owner.email is present it is checked against your account's email or the token's email and rejected with 403 on a mismatch. That is what catches a CI job running with the wrong token. Shared team tokens still work.

Safe to run on every push

Applying is keyed on your account plus name. The first call creates, every call after updates in place. Two different accounts can each have a deployment called my-app without collision.

Private repo tokens

A repo.token is stored with the deployment configuration so builds can clone, and is redacted from every API response and build log. It is never echoed back to you.
